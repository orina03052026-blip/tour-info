# 2026-05-09 に判明した本当の原因

5/8 のメモでは「fill_missing_dates が未実行だから 213 日欠落」と書いていたが、
実際は **fill_missing_dates を実行しても 5 分以内に元に戻る**状態だった。
（5/9 10:21 に added=1244 で成功 → 5/9 11:24 時点で 57 日に戻っていた）

真因はデプロイ中の `syncAvailability`（5 分おきの時間トリガーで動いている）の作りで、

- targetDates を「今日 + 明日 + カレンダーに予定がある日 + Manual Lock 行」だけで構成
- replaceSheetRows_ で **シート全消去** → targetDates の日だけ書き戻し
- → カレンダーに予定が無く Manual Lock も無い日付の行は毎回消える

なので fill_missing_dates が 311 日分の行を追加 → syncAvailability が次の実行で全部消す、
というイタチごっこになっていた。`fill_missing_dates` 自体には問題なかった。

# 2026-05-09 にやったこと（このセッション）

1. デプロイ中の `syncAvailability` の中身を `apps_script/sync_availability.gs` に保存
2. 同ファイル内の `syncAvailability` 関数の targetDates 組み立て部分を、
   「今日 〜 今日 + syncDays(365) を必ず全部入れる」に変更（差分はそこだけ）
3. これにより、syncAvailability 単独で全日付が必ず埋まる作りになった
4. fill_missing_dates 系は不要（廃止）。

# 既知の注意点 / 罠

- syncAvailability は **シートを毎回全消去 → 再構築する設計**。
  したがって「targetDates に含まれない日付の行は必ず消える」のは仕様。
  欠落を直すなら fill ではなく targetDates 側を直すのが正解。
- スプレッドシートの「共有」が崩れると HP 側でデータが出なくなる
  → 「リンクを知っている全員（閲覧者）」必須
- /export?format=csv&gid=0 を使用（「ウェブに公開」CSVは Google が最大 5 分
  キャッシュするので使わない）
- ヘッダー名（Date / Staff / Time Slot / Status / Tour / Booked / Capacity /
  Notes / Source / Manual Lock）が変わると stop する仕様
